## 0. 前提の整理 — 何が変わり、何が変わらないか

- **変わった前提**: クレジットは期限付き（§1-1）で、使わなかった分は失効して消える。
  「課金を極力抑える」は節約ではなく、期限付きリソースを前にした遠慮だった
- **変わらない前提**: **目的は証跡の取得であり、クレジットは手段**。余らせて失効しても損失は
  ゼロだが、**使い切ると spendingLimit: On のためサブスクリプションが無効化され、PostgreSQL を
  含む全リソースが停止**する。ドリル中に踏めば計測記録ごと失われる。**金より証跡が高い**
- したがって本計画は「使い切る」計画ではなく、**上限（§8）とガードレール（§9）の内側で、
  時間をかけないと取得できない証跡を取り切る**計画である

### 証跡の 2 分類（本計画の骨格）

| 分類 | 性質 | 扱い |
| --- | --- | --- |
| **(a) 時間が価値を生む観測** | autovacuum の自然発火、bloat の時系列、閾値レンジ、PITR 復元ウィンドウの拡大、バックアップ/WAL の推移、可用性 SLI、計画メンテ遭遇 | **動かし続ける**（約 1.0〜2.1 USD/日 = §1-3。上限内に収まる。削るのは最後） |
| **(b) イベントの計測** | B1ms→GP スケール、HA 有効化/無効化、planned / forced failover | **時間を区切る**。HA を何日置いてもフェイルオーバーの計測値は良くならない。**測ったら戻す** |

なぜ後継文書か: 旧計画は「Day 4 / Day 5」の日単位詰め込みが骨格で、本書は「(a) の期間観測 +
(b) の時間を区切ったイベント計測」が骨格。章構成ごと変わるため旧文書内改訂では差分が読めない。

## 3. 「クレジットに余裕があるからこそ取れる観測」の採否（すべて (a)）

| # | 観測 | 採否 | 根拠 / 方法（採取の実装は #104） |
| --- | --- | --- | --- |
| 1 | autovacuum の**自然**発火 | **採用** | 合成では絶対に取れない（発火の瞬間を狙って作る合成と、閾値をワークロードが自然に越える観測は別物。閾値はテーブルによって別式で、カウンタ行は dead tuple 側の `50 + 0.2 × reltuples`、heartbeat は insert 側の `1000 + 0.2 × reltuples` = §5-3 / §5-4）。`pg_stat_user_tables` の `n_dead_tup` / `last_autovacuum` / `autovacuum_count` をスナップショット採取 |
| 2 | bloat の時系列（鋸歯） | **採用** | `pgstattuple` の定期採取。1 点の測定より説得力が桁違い。**通常の autovacuum の後に落ちるのは `dead_tuple_percent` だけで、`table_len` は縮まず `free_percent` が上がる**（領域は再利用のためテーブル内に保持され、OS へは返らない。OS へ返すのは `VACUUM FULL` / `pg_repack`。本プロジェクトは通常 VACUUM のみで、`VACUUM FULL` は実行しない）。この 3 系列の波形をそのまま取る |
| 3 | 監視閾値の実測レンジ | **採用** | CPU / メモリ / 接続数 / ストレージ / IOPS の分布から「p95 + マージン」で閾値を決める（旧計画 §7 の要求そのもの）。Azure Monitor メトリクスは Azure 側に 93 日保持されるため採取は日次エクスポートで足りる |
| 4 | PITR 復元ウィンドウの拡大 | **採用** | サーバー再作成直後の今は幅がほぼない。**8/29 頃に保持 7 日の窓が満杯になり `earliestRestoreDate` が動き出す**（この「窓がスライドし始める瞬間」自体が時間でしか取れない観測）。2 回目ドリルで 24 時間以上前へ復元 |
| 5 | バックアップ使用量の推移 | **採用** | 日次チェックで記録済みの項目を継続 + 無料枠 32GB との突き合わせ。保持 7 日（ADR-0011）の決定根拠を実測で裏付ける |
| 6 | WAL 生成レート | **採用** | PG17 の `pg_stat_wal`（`wal_records` / `wal_bytes`）をスナップショット採取。継続書き込み下の生成レート → 容量計画・バックアップサイズの話につなぐ |
| 7 | 可用性・レイテンシ SLI | **採用** | #106 の外形監視。コールドスタート 22.7 秒は 1 回きりの観測で**再現性未確認** → 分布を取る |
| 8 | 計画メンテナンス遭遇 | **採用（受動）** | 数日動かして当たれば「メンテ中に止まりましたか」への実測回答。当たらなければ**当たらなかったと記録**する。maintenance window 設定値と Service Health を日次チェックに含める |
| 9 | 「何も起きなかった」記録 | **採用** | 安定稼働 N 日・probe 成功率・Job 成功率として定量化（沈黙ではなく数字で残す） |
| 10 | XID 消費と frozen age の推移 | **採用（追加。候補外）** | `age(datfrozenxid)` の進み方を継続書き込み下で記録。wraparound 対策（autovacuum の第二の役割）を実データで語れる。採取は 1 行の SQL で追加コストほぼ 0 |

### 5-3. 採取の設計（#104 の実装仕様。根拠つき）

> **この毎分の書き込みの位置づけ**: PITR の復旧時点を確定させるための
> **recovery marker**（既知の書き手）であり、autovacuum / bloat を駆動する**負荷生成ではない**。
> 正本は [ADR-0021](../adr/0021-heartbeat-table-as-recovery-marker.md)。
> 負荷生成（churn generator）は §5-5 の別装置（#112 / PR #120。未マージ）。

- **書き込み（観測対象を作る側）**: heartbeat INSERT 1 行/分 + カウンタ行 UPDATE 1 回/分。
  dead tuple の供給源はこの UPDATE（1,440 dead tuples/日）。heartbeat テーブルは INSERT-only で
  dead tuple がほぼ出ないため、効くのは **insert-vacuum 側の閾値 `1000 + 0.2 × reltuples`** であり、
  dead tuple 側の閾値 `50 + 0.2 × reltuples` ではない（両者は別の条件。詳細は §5-4）。
  閾値は `reltuples` の増加とともに上がるため、**発火間隔が日を追って延びる
  過程そのものが §3-1 の観測になる**
- **スナップショット採取（観測する側）**: 同じ cron Job 実行内で `pg_stat_user_tables` /
  `pg_stat_wal` / `age(datfrozenxid)` / DB サイズを **5 分間隔**で観測用テーブル
  （INSERT-only）へ保存。`pgstattuple` のみ **1 時間間隔**
  - 5 分の根拠: `last_autovacuum` / `autovacuum_count` は正確な時刻を持つため、採取は発火を
    「挟めれば」よく、1 分採取は情報を増やさない。粗すぎると `n_dead_tup` の鋸歯の立ち上がりを
    潰す。5 分で 1 日 288 点 = 発火前後の形が十分残る
  - `pgstattuple` を 1 時間にする根拠: 実テーブルのフルスキャンを伴う観測で、**観測が観測対象に
    与える影響が最大の項目**（バッファ・I/O）。bloat の変化スケール（時間〜日）に対して 1 時間で
    十分な分解能
- **採取先は DB 内の観測用テーブル**（Log Analytics ではなく）。根拠: (i) SQL でそのまま
  時系列分析でき、成果物の証跡としてダンプも取れる、(ii) Log Analytics は取込課金と
  スキーマ設計が増えるうえ、DB 内部統計を外に出す変換層が要る、(iii) 観測テーブル自体が
  バックアップサイズ推移（§3-5）の一部になる。**トレードオフ**: PITR ドリルで復元した
  サーバー側の観測テーブルは復元時点までしか持たない（ドリル記録は従来どおり
  `docs/verification/` に別途残すので問題ない）
- **観測者効果の明記**: 採取自体も書き込み（5 分ごと数行 INSERT + 1 時間ごとのフルスキャン読み）
  であり、WAL / バックアップ / bloat の測定値に採取分が混入する。観測用テーブルを専用スキーマに
  分離し、テーブル別の統計（`pg_stat_user_tables` はテーブル単位）で**heartbeat 系と観測系を
  分けて記録**することで、混入を定量化可能にする
- **無音失敗の防止（最悪 =「3 日前から止まっていた」）**: 3 層で守る
  1. Job execution の失敗は日次チェック（§5-2）で数える
  2. **鮮度ゲート（系列ごと）**: /readyz の応答に **3 系列それぞれの最新レコード経過秒**を
     含める改修（#104/#106 で設計）を入れ、外形監視が系列別の閾値超過で workflow を fail させる
     → GitHub の失敗通知で即日検知（probe の生存確認と採取の生存確認を 1 本に束ねる）。
     「heartbeat だけ新しくて統計採取が 3 日前に止まっている」を防ぐため、**束ねた 1 値ではなく
     系列別に判定**する。閾値: heartbeat **10 分** / 統計スナップショット **15 分** /
     pgstattuple **3 時間**。根拠: probe 間隔（5 分）以上であること + 採取間隔の約 3 倍 =
     一時的失敗 2 回まで許容し 3 回連続相当で fail（cron ジッタ・一過性エラーでの誤報防止。
     heartbeat は 1 分間隔だが 3 分では probe 間隔より短く判定不能のため probe 間隔の 2 倍 = 10 分）
  3. 週次の集計（probe 成功率・Job 成功数）で取りこぼしを拾う

### 5-4. 観測期間の長さ: 分析と決定（**72h に決定。2026-08-23**）

「観測値がないと根拠のある設計判断ができない。でも早く仕上げたい」という要求に対する分析
（比較表は記録として保存）。

**決定（2026-08-23 ユーザー）: フェーズ 1 = 72h + フェーズ 2（高負荷観測 = §5-5）を追加**。

決定の経緯（推奨 96h から変わった理由。記録）:

- ユーザーから「**この PostgreSQL は DB も RAG もデータ量が極小なのに、その監視に意味があるのか**」
  という問いがあり、coordinator はこれを正しい指摘として認めた。整理:
  - **意味が薄い**: 監視の閾値の数値そのもの・bloat の絶対量・容量計画（毎分 1 件の書き込みで
    B1ms を回してもアイドル付近に張り付き、そこから出る閾値はこの人工的な無負荷状態に対する
    ものでしかない）
  - **意味が残る**: (1) 可観測性のループを作りアラートが実際に発火することを実証したこと
    （数値でなく手順が転用可能）、(2) autovacuum を**パラメータから事前計算して予測どおりに
    発火させ記録する**こと（データが小さく完全に見通せるからこそ成立する）、(3) PITR / HA は
    データ量依存が小さい
- この整理から、96h 案が 72h 案より優れる主根拠だった「カデンツ 4 点目」（**当時の誤った予測式による点数。補正後は 96h = 3 点 / 72h = 2 点**）は
  「意味が薄い」と自認した側を補強するだけであり、**72h + フェーズ 2（前後比較）のほうが
  批判に正面から答えられる**と判断が変わった。「後で高負荷で観測し直す」は後付けではなく
  §5-5 として計画に織り込む

#### 前提: autovacuum パラメータの実測（2026-08-23、ops 経由 `pg_settings`。すべて既定値のまま）

| パラメータ | 実測値 |
| --- | --- |
| `autovacuum_vacuum_threshold` / `_scale_factor` | 50 / 0.2 |
| `autovacuum_vacuum_insert_threshold` / `_insert_scale_factor` | 1000 / 0.2 |
| `autovacuum_analyze_threshold` / `_scale_factor` | 50 / 0.1 |
| `autovacuum_naptime` / `autovacuum_max_workers` | 60s / 3 |

#### 各観測項目の律速要因（カレンダーか、書き込みレートか）

発火に必要な書き込み量を実測パラメータから計算すると:

- **カウンタ行（UPDATE 毎分・N=1）**: 発火閾値 = 50 + 0.2×1 ≈ **50 dead tuples → 約 50 分周期で
  自然発火**（1 日 ~29 回）。複数回の発火は**数時間で**満たされる
- **heartbeat テーブル（INSERT 毎分・insert-vacuum）**: 閾値は
  `autovacuum_vacuum_insert_threshold + autovacuum_vacuum_insert_scale_factor × reltuples`
  = `1000 + 0.2 × reltuples`。**当初の予測は外れた。訂正の経緯を残す（当初 2026-08-23 / 訂正 2026-08-26）**:
  - **当初（誤）**: 閾値の `reltuples` を「**前回 vacuum 時点の行数**」として計算し、発火時刻を
    **16.7h → 36.7h → 60.7h → 89.5h → 124.0h → 165.5h**（1440 行/日）= 3 日で 3 回と予測した
  - **実測（フェーズ 1）**: 初回発火は **20.5h**。観測開始 2026-08-23 07:16:18 に対し
    `last_autovacuum` = 2026-08-24 03:46:39（20 時間 30 分 21 秒）。予測から約 3.8 時間ずれた
  - **原因**: `pg_class.reltuples` は VACUUM だけでなく **ANALYZE でも更新される**。
    PostgreSQL 17 公式は reltuples を
    "It is updated by `VACUUM`, `ANALYZE`, and a few DDL commands such as `CREATE INDEX`." と定義する。
    heartbeat テーブルは analyze 側の閾値 `50 + 0.1 × reltuples` を INSERT だけで頻繁に越えるため、
    `reltuples` は「前回 vacuum 時点の行数」ではなく **ほぼ現在行数に追随する**。
    つまり vacuum を待つ間も閾値が上がり続けるので、当初の計算は発火を早く見積もりすぎていた
  - **補正式**: 前回 vacuum 以降に挿入した行数 m が
    `m > 1000 + 0.2 × (前回 vacuum 時点の行数 + m)` を満たした時に発火する。
    初回は前回 vacuum 時点 0 行なので `0.8 m > 1000` → **m = 1250 行 = 1250 分 = 20.8h**。
    実測 20.5h と一致する（実測がわずかに早いのは `reltuples` が直近 ANALYZE 時点の値で
    現在行数よりやや小さく、閾値もその分低くなるため。差は naptime 60s の分解能の範囲）
  - **補正後の予測系列**: 発火間隔は公比 1.25 の等比列になり、発火時刻は
    **20.8h → 46.9h → 79.4h → 120.1h → 171.0h**。つまり **3 日で 2 回・4 日で 3 回・7 日で 4 回**。
    **「発火間隔が伸びていく曲線」の点数だけが日数に比例する**という結論自体は変わらない
- 分類:

| 観測（§3 の #） | 律速 | 必要日数の下限 |
| --- | --- | --- |
| 1 autovacuum 発火・2 bloat 鋸歯・6 WAL・10 XID age | **書き込みレート**（上の計算のとおり現行の書き込み設計のままで充足） | カウンタ系は数時間。heartbeat の伸びる曲線のみ日数比例（補正後: 2 点 = 3 日、3 点 = 4 日） |
| 3 閾値レンジ・7 SLI・5 バックアップ推移・11 LA 取込 | **カレンダー（日内・日次周期）** | 周期 2〜3 回 = 2〜3 日で形は出る。日数は分布の n（SLI: 288 点/日）と p95 の安定を買う。**注**: ここで得る「閾値」はフェーズ 1 の負荷特性に対するもの（成果物の書き方は §5-4 = 閾値の数値でなく可観測性ループの実証を主張する） |

### 5-5. フェーズ 2: 高負荷観測（2026-08-23 ユーザー決定で追加。実装 Issue は #112）

フェーズ 1（低負荷ベースライン）と**同一の採取（方法・間隔・テーブルすべて不変。変わるのは
`obs.phase_config` のラベルだけ = #104 のフェーズ識別）**で、高負荷時のレンジを測って前後比較する。
「データ量が小さいから意味がない」という批判に、比較データで正面から答えるための設計。

#### 仮説（**すべて仮説。まだ何も測っていない**）と検証方法

| # | 仮説 | 検証方法 |
| --- | --- | --- |
| H1 | dead tuple の生成が autovacuum の処理を上回る「**追いつかない状態**」を作れる（実運用の典型的障害モード） | `obs.table_stats` の `n_dead_tup` が発火（`autovacuum_count` 増加）をまたいで単調増加するかを phase='load' の系列で確認 |
| H2 | **bloat が量として測れる**（フェーズ 1 では微小すぎる） | `obs.bloat_stats` の `dead_tuple_percent` / `free_percent` を phase 間で比較 |
| H3 | **B1ms は継続負荷で CPU クレジットが枯渇し、ベースライン CPU に制限されて性能が劣化する** | Azure Monitor の **CPU Credits Remaining**（下記一次情報が名指しするメトリクス）+ 負荷生成側のスループット / レイテンシログ + probe（#106）のレイテンシ。**機構は一次情報で確認済み・発生までの時間と劣化の程度は未実測** |

H3 の一次情報（[Compute options](https://learn.microsoft.com/en-us/azure/postgresql/compute-storage/concepts-compute)、2026-08-23 取得。逐語）:

> Uses a CPU credit model: credits accumulate when usage is below baseline and are consumed when
> usage exceeds it. When credits are exhausted, the VM is restricted to baseline CPU, which under
> sustained load can cause severe performance degradation, connection timeouts, and delays or
> transient failures in management operations until credits rebuild.
>
> Not recommended for production workloads.
>
> Monitor **CPU Credits Remaining** in Azure Monitor and set alerts for low credits.

#### 負荷生成の設計（フェーズ 1 を汚さない。実装 = #112）

- **専用 `load` スキーマ**のテーブルのみに書き込む（obs / public に触れない）。採取側は
  'load' スキーマを既に対象に含めてある（#104。テーブルが無い間は行が出ないだけ）

  フェーズ 1 の間は一度も起動しない = ベースラインへの混入はゼロ
- フェーズ遷移手順（Issue #114 の 1 で改訂）: 負荷開始の直前に `'load'`、GP 昇格直後に
  `'gp_load'`、負荷終了・B1ms 復帰後に `'cooldown'`（比較の分析単位）。遷移は次の **1 文**で
  行う（`obs.phase_config` は 1 行上書きで履歴が残らないため、追記専用の `obs.phase_log`
  （migration 0003）へ同時に記録する。1 文の CTE なら履歴の書き忘れが構造的に起きない）:

  ```sql
  WITH t AS (
    UPDATE obs.phase_config SET phase = 'load', since = now() WHERE id = 1
    RETURNING phase, since
  )
  INSERT INTO obs.phase_log (phase, since) SELECT phase, since FROM t;
  ```

  累積カウンタの差分で読むため、フェーズ境界直後の最初の 1 行は 2 フェーズをまたぐ
  累積差分になる（table_stats / db_stats は最大 5 分、bloat_stats は最大 1 時間分）。
  フェーズ間比較では各フェーズの先頭 1 スナップショットを除外してから集計する
- 観測者効果の整理（§5-3）との整合: 採取側は不変のまま。負荷生成そのものは「観測対象の
  ワークロード」であって観測者ではない（フェーズラベルで分離されるため、フェーズ 1 の

## 9. 打ち切り基準と失効前手順

**打ち切りの優先順位（消費が想定を超えたとき。上から順に止める）**:

1. **(b) を止める**: HA 無効化 → B1ms へ戻す（イベント計測は途中でも、取れた分が証跡）
2. **Azure OpenAI 経路を止める**: /chat 無効化（保護方式によらず環境変数で塞げる設計を #107 に含める）
3. **(a) は最後まで守る**: それでも足りない場合の最終手段は
   「**証跡の即時退避 → ephemeral destroy → 実体確認**」の順で行う:
   1. 観測テーブルのダンプ・probe ログ集計・メトリクスエクスポート（失効前手順の 1 と同じ内容を
      前倒し実行）。**退避が先** — ephemeral destroy で ops = DB への唯一の対話経路が消えるため、
      後回しにすると証跡ごと失う
   2. `terraform -chdir=terraform/ephemeral destroy`
   3. **実体確認**: `az containerapp replica list` 相当での実レプリカ消滅と
      `az resource list` での残存リソースゼロを確認（設定値でなく実体を見る = G4 の教訓）

   PostgreSQL（persistent）と退避済みデータ（＝証跡）は最後の最後まで残す。
   **旧版の「ops min 0 化 → 常駐停止」は削除**: min 0 でも ops のレプリカは落ちず active 課金が
   続くことが実測で確定済み（observations.md「G4 の訂正」/ ADR-0015 追記 #100）で、止血にならない
   （この自己矛盾は外部レビューが検出した。経緯は observations.md 同節の付記）

**判定則は (a) と (b) で分ける**（結論: 分けるべき。理由 — (a) はワースト日額 2.1 USD で、
検知が 2 日遅れても被害は約 4 USD に収まり、誤中断で観測の連続性を失う損失のほうが大きい。
(b) は 12 USD/日で、事後検知では開始した瞬間に余白 6 USD の超過が確定してから気づくことになり、
構造的に間に合わない）:

- **(a) 常時観測 = 事後検知型（従来どおり）**: 日次チェックで「estimated の日次差分 × 残日数 +
  既消費」が上限 90 USD を超える見込みが **2 日連続**になったとき発動（1 日分のラグ起因の振れで
  誤中断しない）
- **(b) イベント計測 = 事前予約型 + 壁時計強制終了**: 事後検知は適用しない。
  開始条件と強制終了は §6 の 1 / 1-b が正本（開始前に費用を全額予約し、開始後は課金表示と
  無関係に時刻で戻す）

**teardown の手順**（**2026-09-14〜09-15 目安**。作業窓の再設定 = §10-5。証跡を取り切ってから畳む）:

1. 9/14: 観測データの最終エクスポート（観測テーブルのダンプ → `docs/verification/` 証跡化、
   probe ログ集計、Azure Monitor メトリクスの必要範囲エクスポート — **CPU Credits Remaining を含む**）
2. 9/15: **外形監視の停止**（`gh variable set PROBE_ENABLED --body false` — FQDN が消えた後に
   5 分ごとの fail 通知が永久に出続けるのを防ぐ）
   → ephemeral destroy → persistent destroy（旧計画 §5-6 の手順。Azure Monitor の 6 件
   = メトリクスアラート 5 + Action Group 1 は 2026-08-27 に persistent 層へ import 済みのため
   （Issue #151 / ADR-0022）、persistent destroy が依存の逆順で消す。手動削除の一手は不要）
   → 残存リソースゼロ確認
3. 9/16 以降: 課金反映ラグの分を待って最終コスト実測を記録（これも FinOps 証跡）。**失効 9/18T06:59Z までに完了する必要がある**（失効後はサブスクリプション無効化で取得自体ができない）

- **マージンは 2 層に分かれる**（2026-08-30 の作業窓再設定 = §10-5 による。以前の「約 14 日」は
  teardown 9/4 時代の値で、もう成立しない）:
  - **作業窓のテール = 約 12 日**（予定最終作業 9/2 目安 → teardown 9/14〜9/15）。日程の遅延・
    万一の観測やり直しはここで吸収する
  - **teardown 後のテール = 3 日**（teardown 9/15 → 失効 9/18T06:59Z）。teardown 失敗時の調査・
    再実行と、反映ラグ待ちの「最終消費額」確定に使える余地はここまで
- **3 日は反映ラグの仮定 L = 2 日（§6）を 1 日しか上回らない**。最終消費額の確定は失効後でも
  Cost Management 側に残る可能性があるが**未検証**であり、確定を失効前に間に合わせる前提では
  余裕が薄い。失効後はサブスクリプション無効化で**記録の取得自体ができなくなる**、という制約は不変

## 10. 決定事項（2026-08-22 / 08-23 / 08-30 ユーザー決定）と本計画で結論を出した論点

### 10-1. 決定: 総消費上限 = 90 USD（2026-08-23 更新。当初 75。**2026-08-30 に 150 へ再更新 = §10-5**。本節は 75 → 90 の経緯の記録）

- 当初決定（2026-08-22）: 75 USD。根拠 = 期待 69 / ワースト 96 の積み上げに対し「(b) を 1 回
  やり直せる」余地（60 USD 案との差額 15 USD）。採用理由は「**失敗した計測は証跡にならない。
  やり直せずに終わるほうが、15 USD 多く使うことより痛い**」
- 更新（2026-08-23）: **90 USD**。外部レビューを受けて事前予約方式のゲート（§6）を導入し
  実計算したところ、**75 では「(b) をやり直せる」という当初の前提が成立しない**ことが判明した
  （フル予約は下限実績 1.0 USD/日ですら 76.9 > 75。§8-1 の参考値）。**75 という数字が誤りだった
  のではなく、それを支える前提が実計算で更新された**。90 なら期待実績までフル予約が通り、
  ワーストでも標準予約で (b) フル構成が成立する（§8-1）。残高 199.83 に対し 45% で、
  spendingLimit までの距離も十分（使い切り = 全停止のリスク管理は §0 / §9 のまま）

### 10-2. 決定: /chat 保護 = (a) アプリ層 API キー + (d) 緊急遮断フラグの併設（#107）

検討した 5 案と消去法の結論（決定 2026-08-22）:

### 10-3. 決定: フェーズ 1 = 72h + フェーズ 2（高負荷観測）の追加（2026-08-23）

### 10-4. 本計画で結論を出した論点（再掲）

- (b) は**時間を区切る**（2 日。§6 に根拠）— HA 多日常駐案は棄却（時間が計測値を良くしない）
- 合成テストと自然発火観測は**併用**（§7-1。代替でなく補完）
- 閾値レンジの収集は **フェーズ 1 = T_obs_start + 72h（2026-08-23 決定。§5-4）+ フェーズ 2 の
  高負荷レンジとの前後比較（§5-5）**。当初の「最低 7 日」根拠は §5-4 の分析で「大部分が自分で
  課した制約」と判明し、以下の記録は当時の判断として残す。当時の最低 7 日（= 168h）の根拠:
  我々の書き込みレートで autovacuum の発火を複数回・バックアップの日次周期・probe の日内変動を
  各複数回含むこと。営業日変動のない一定レートの書き込み（recovery marker 1 行/分 +
  カウンタ 1 行 UPDATE/分。負荷生成ではない = [ADR-0021](../adr/0021-heartbeat-table-as-recovery-marker.md)）
  のため週次の季節性は考慮不要
- 採取先は DB 内観測テーブル・間隔は 5 分（pgstattuple のみ 1 時間）（§5-3 に根拠と観測者効果）
- teardown は **2026-09-15 目安**（§9 / §10-5。当初 9/16 想定 → 72h 化で 9/3〜9/4 へ前倒し →
  2026-08-30 の作業窓再設定で 9/15 へ。失効 9/18 まで 3 日のマージン）
- 外部レビュー反映（2026-08-23）: 観測期間は日付固定でなく**相対時刻**（現行は T_obs_start + 72h。§2）、
  打ち切り判定則は **(a) 事後検知型 / (b) 事前予約型 + 壁時計強制終了**に分離（§6 / §9）、
  時間・費用の削減優先順位は **(b) 再試行 → PITR 2 回目 → (b) 本体縮小**で一本化（§2）、
  最終手段は「証跡退避 → ephemeral destroy → 実体確認」（§9。min 0 は止血にならない実測に整合）

**なぜ 9/3〜9/4 を捨てたか**: 9/3〜9/4 は「フェーズ 1 を 72h に短縮したぶん teardown も前倒しできる」

唯一の硬い締め切りは失効 9/18 であり、前倒しは「使わずに失効するクレジット」を増やすだけで
何も買っていない（ADR-0020 の「節約は価値を生まない」と同じ論法）。作業窓を失効直前まで伸ばし、
teardown 後のマージンを 3 日に絞るのは、**残った 12 日ぶんの (a) 観測機会を捨てないため**である。

**なぜ上限を 150 へ上げたか**: teardown が 9/15 になると (a) ベースラインの日数が 13 → 24 日に増え、
§8 の積み上げはワースト **95 USD** となって上限 90 を超える。§8-1 のゲート計算でも
ワースト実績でのフル予約が 94.6 > 90 で不成立になる。**上限 90 のままでは teardown 9/15 を
計画として立てられない**ため、上限側を引き上げた（§10-1 の 75 → 90 と同じ構造の更新）。
150 は残高 199.83 の約 75% で、`spendingLimit` に到達して全停止する余地は残る。
なお **2026-08-30 実測の 0.30 USD/日で置き直すと (a) は 24 日で約 7 USD**（§8）であり、
上限 150 の逼迫は現時点で想定されない。
