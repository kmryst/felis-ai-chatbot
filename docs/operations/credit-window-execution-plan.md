## 0. 前提の整理 — 何が変わり、何が変わらないか

- **変わった前提**: クレジットは期限付き（§1-1）で、使わなかった分は失効して消える。
  「課金を極力抑える」は節約ではなく、期限付きリソースを前にした遠慮だった
- **変わらない前提**: **目的は証跡の取得であり、クレジットは手段**。余らせて失効しても損失は
  ゼロだが、**使い切ると spendingLimit: On のためサブスクリプションが無効化され、PostgreSQL を
  含む全リソースが停止**する。ドリル中に踏めば計測記録ごと失われる。**金より証跡が高い**
- したがって本計画は「使い切る」計画ではなく、**上限（§8）とガードレール（§9）の内側で、
  時間をかけないと取得できない証跡を取り切る**計画である

### 証跡の 2 分類（本計画の骨格）

| 分類 | 性質 | 扱い |
| --- | --- | --- |
| **(a) 時間が価値を生む観測** | autovacuum の自然発火、bloat の時系列、閾値レンジ、PITR 復元ウィンドウの拡大、バックアップ/WAL の推移、可用性 SLI、計画メンテ遭遇 | **動かし続ける**（約 1.0〜2.1 USD/日 = §1-3。上限内に収まる。削るのは最後） |
| **(b) イベントの計測** | B1ms→GP スケール、HA 有効化/無効化、planned / forced failover | **時間を区切る**。HA を何日置いてもフェイルオーバーの計測値は良くならない。**測ったら戻す** |

なぜ後継文書か: 旧計画は「Day 4 / Day 5」の日単位詰め込みが骨格で、本書は「(a) の期間観測 +
(b) の時間を区切ったイベント計測」が骨格。章構成ごと変わるため旧文書内改訂では差分が読めない。
旧計画の §2-1（No.1〜31）/ §2-2 は出典と実測の台帳として残す。

## 3. 「クレジットに余裕があるからこそ取れる観測」の採否（すべて (a)）

| # | 観測 | 採否 | 根拠 / 方法（採取の実装は #104） |
| --- | --- | --- | --- |
| 1 | autovacuum の**自然**発火 | **採用** | 合成では絶対に取れない（発火の瞬間を狙って作る合成と、閾値 `0.2×N+50` を実ワークロードが自然に越える観測は別物）。`pg_stat_user_tables` の `n_dead_tup` / `last_autovacuum` / `autovacuum_count` をスナップショット採取 |
| 2 | bloat の時系列（鋸歯） | **採用** | `pgstattuple` の定期採取。1 点の測定より説得力が桁違い。vacuum 後に落ちる波形まで取る |
| 3 | 監視閾値の実測レンジ | **採用** | CPU / メモリ / 接続数 / ストレージ / IOPS の分布から「p95 + マージン」で閾値を決める（旧計画 §7 の要求そのもの）。Azure Monitor メトリクスは Azure 側に 93 日保持されるため採取は日次エクスポートで足りる |
| 4 | PITR 復元ウィンドウの拡大 | **採用** | サーバー再作成直後の今は幅がほぼない。**8/29 頃に保持 7 日の窓が満杯になり `earliestRestoreDate` が動き出す**（この「窓がスライドし始める瞬間」自体が時間でしか取れない観測）。2 回目ドリルで 24 時間以上前へ復元 |
| 5 | バックアップ使用量の推移 | **採用** | 日次チェックで記録済みの項目を継続 + 無料枠 32GB との突き合わせ。保持 7 日（ADR-0011）の決定根拠を実測で裏付ける |
| 6 | WAL 生成レート | **採用** | PG17 の `pg_stat_wal`（`wal_records` / `wal_bytes`）をスナップショット採取。継続書き込み下の生成レート → 容量計画・バックアップサイズの話につなぐ |
| 7 | 可用性・レイテンシ SLI | **採用** | #106 の外形監視。コールドスタート 22.7 秒は 1 回きりの観測で**再現性未確認** → 分布を取る |
| 8 | 計画メンテナンス遭遇 | **採用（受動）** | 数日動かして当たれば「メンテ中に止まりましたか」への実測回答。当たらなければ**当たらなかったと記録**する。maintenance window 設定値と Service Health を日次チェックに含める |
| 9 | 「何も起きなかった」記録 | **採用** | 安定稼働 N 日・probe 成功率・Job 成功率として定量化（沈黙ではなく数字で残す） |

### 5-3. 採取の設計（#104 の実装仕様。根拠つき）

- **書き込み（観測対象を作る側）**: マーカー INSERT 1 行/分 + カウンタ行 UPDATE 1 回/分。
  dead tuple の供給源はこの UPDATE（1,440 dead tuples/日）。マーカーテーブルの
  autovacuum 閾値（0.2×N+50）は N の増加とともに上がるため、**発火間隔が日を追って延びる
  過程そのものが §3-1 の観測になる**
- **スナップショット採取（観測する側）**: 同じ cron Job 実行内で `pg_stat_user_tables` /
  `pg_stat_wal` / `age(datfrozenxid)` / DB サイズを **5 分間隔**で観測用テーブル
  （INSERT-only）へ保存。`pgstattuple` のみ **1 時間間隔**
  - 5 分の根拠: `last_autovacuum` / `autovacuum_count` は正確な時刻を持つため、採取は発火を
    「挟めれば」よく、1 分採取は情報を増やさない。粗すぎると `n_dead_tup` の鋸歯の立ち上がりを
    潰す。5 分で 1 日 288 点 = 発火前後の形が十分残る
  - `pgstattuple` を 1 時間にする根拠: 実テーブルのフルスキャンを伴う観測で、**観測が観測対象に
    与える影響が最大の項目**（バッファ・I/O）。bloat の変化スケール（時間〜日）に対して 1 時間で
    十分な分解能
- **採取先は DB 内の観測用テーブル**（Log Analytics ではなく）。根拠: (i) SQL でそのまま
  時系列分析でき、成果物の証跡としてダンプも取れる、(ii) Log Analytics は取込課金と
  スキーマ設計が増えるうえ、DB 内部統計を外に出す変換層が要る、(iii) 観測テーブル自体が
  バックアップサイズ推移（§3-5）の一部になる。**トレードオフ**: PITR ドリルで復元した
  サーバー側の観測テーブルは復元時点までしか持たない（ドリル記録は従来どおり
  `docs/verification/` に別途残すので問題ない）
- **観測者効果の明記**: 採取自体も書き込み（5 分ごと数行 INSERT + 1 時間ごとのフルスキャン読み）
  であり、WAL / バックアップ / bloat の測定値に採取分が混入する。観測用テーブルを専用スキーマに
  分離し、テーブル別の統計（`pg_stat_user_tables` はテーブル単位）で**マーカー系と観測系を
  分けて記録**することで、混入を定量化可能にする
- **無音失敗の防止（最悪 =「3 日前から止まっていた」）**: 3 層で守る
  1. Job execution の失敗は日次チェック（§5-2）で数える
  2. **鮮度ゲート（系列ごと）**: /readyz の応答に **3 系列それぞれの最新レコード経過秒**を
     含める改修（#104/#106 で設計）を入れ、外形監視が系列別の閾値超過で workflow を fail させる
     → GitHub の失敗通知で即日検知（probe の生存確認と採取の生存確認を 1 本に束ねる）。
     「マーカーだけ新しくて統計採取が 3 日前に止まっている」を防ぐため、**束ねた 1 値ではなく
     系列別に判定**する。閾値: マーカー **10 分** / 統計スナップショット **15 分** /
     pgstattuple **3 時間**。根拠: probe 間隔（5 分）以上であること + 採取間隔の約 3 倍 =
     一時的失敗 2 回まで許容し 3 回連続相当で fail（cron ジッタ・一過性エラーでの誤報防止。
     マーカーは 1 分間隔だが 3 分では probe 間隔より短く判定不能のため probe 間隔の 2 倍 = 10 分）
  3. 週次の集計（probe 成功率・Job 成功数）で取りこぼしを拾う

## 6. イベント計測 (b)（9/9〜9/10 の 2 日間。測ったら戻す）

順序と各計測（手法は旧計画 §5 のまま。1 秒間隔疎通ループ + #106 の外形監視の両方で取る）:

1. 実行前チェック（**開始可否の事前予約判定**。事後検知では間に合わないため、費用を開始前に
   全額予約する）: `plan -detailed-exitcode` exit 0 / GP の無料枠除外の公式再確認 / 次の不等式:

   **C_settled + U + B_rem + R_b + R_openai ≤ 75 USD**

   - `C_settled`: balanceSummary の estimated から読める消費実績（判定時点）
   - `U`: **未反映額の上限 = L × D_max**。`L` は課金反映ラグの上限日数で **2 日と仮定**
     （**仮定**: 実測済みなのは「当日分が同日中に未反映」（2026-08-22）までで、ラグの実日数は
     未実測。保守側に 2 日を置き、§5-2 の日次記録で「前日分が何日後に現れるか」を実測して
     上書きする。実測が 2 日を超えたら L を実測値へ引き上げる）。`D_max` は直近 L 日間の
     構成の理論最大日額（ベースライン期 2.1 / (b) 期間中 14.1 = 12.0 + 2.1）
   - `B_rem`: 残期間のベースライン費用 = teardown（9/16）までの残日数 × 2.1（ワースト日額）
   - `R_b`: **イベント予約額 = 30 USD**（(b) ワースト = §8 の 24 + 再試行余地 6。開始前に全額予約
     し、途中の課金表示では判定しない。チェックポイント（§5-2）で段階を落とした場合は
     24（再試行なし）/ 15（縮小構成 = 1 日で GP 昇格 + HA + failover 2 種 + 復旧、遷移込み）を使う）
   - `R_openai`: **残期間の Azure OpenAI 予約 = 10 USD**（§8 ワースト。判定時点までの OpenAI
     既消費が実測で分かる場合は `max(0, 10 − 既消費)` に置き換えてよい。9/9 以降にも PITR 2 回目・
     RAG 検証で OpenAI を使う予定があり、**予約しない支出が予約済みの枠を食う**のを防ぐため、
     過去分（C_settled 内）とは別に将来分を必ず項として立てる。チェックポイントで段階を落とす
     場合は 5 → 3（/chat 遮断フラグで上限を強制）を使う）

1-b. **HA の強制終了時刻（壁時計ベース。課金表示と独立）**: HA 有効化コマンド発行時刻を
   `T_b_start` として記録し、**`T_b_start + 48 時間` で計測の完了状況にかかわらず HA 無効化 →
   B1ms へ戻す**。N = 48h の根拠: §6 の全計測（スケール 2 方向 + HA 有効化/無効化 + failover
   2 種 + 予備再試行）は 2 日で完了する設計で、48h は予約 R_b = 30 USD（12.0 × 2 + 遷移・
   再試行分）と整合する。課金データは反映ラグで嘘をつくが、壁時計は嘘をつかない。
   `T_b_start + 48h` の時刻は開始時に日次チェック（§5-2）の先頭項目に書き込む。
   **縮小構成（R_b = 15。1 日設計）で開始した場合の強制終了は `T_b_start + 24h`**（同じ理屈で
   予約額と壁時計を一致させる）
2. **B1ms → GP 2vCore スケール**（ダウンタイム実測。旧計画 §2-2 No.4）
3. **zone-redundant HA 有効化**（所要時間実測。旧計画 §2-2 No.5）
4. **planned failover** → 復帰確認 → **forced failover**（ダウンタイム実測。旧計画 §2-2 No.6/7）。
   実測値を SLA（zone-redundant 99.99% / HA なし 99.9% = §1-2 の Reliability ページ）と
   突き合わせ、「SLA が保証しないもの（≠ RTO/RPO）」を証跡にする
5. **HA 無効化 → GP → B1ms へ戻す**（戻し方向のダウンタイムも実測。Burstable は HA 非対応の
   ため必ず HA 無効化 → スケールダウンの順）
6. 前後の (a) 観測は止めない（GP 期間中のメトリクスレンジが §3-3 の比較点として残る）

- コスト: GP+HA 12.0 USD/日 × 2 日 = **24 USD**（+ B1ms↔GP の遷移日は按分）。
  **2 日で足りる根拠**: (b) はすべてイベント計測で、上記 4 種 + 予備再試行を 2 日に収められる。
  HA を長く置いても failover の計測値は改善しない（§0）。予備日は §2 のとおり 9/11〜9/12 に
  PITR 2 回目としてスケジュール済みで、(b) が延びた場合はそこを食う（teardown は動かさない）

## 9. 打ち切り基準と失効前手順

**打ち切りの優先順位（消費が想定を超えたとき。上から順に止める）**:

1. **(b) を止める**: HA 無効化 → B1ms へ戻す（イベント計測は途中でも、取れた分が証跡）
2. **Azure OpenAI 経路を止める**: /chat 無効化（保護方式によらず環境変数で塞げる設計を #107 に含める）
3. **(a) は最後まで守る**: それでも足りない場合の最終手段は
   「**証跡の即時退避 → ephemeral destroy → 実体確認**」の順で行う:
   1. 観測テーブルのダンプ・probe ログ集計・メトリクスエクスポート（失効前手順の 1 と同じ内容を
      前倒し実行）。**退避が先** — ephemeral destroy で ops = DB への唯一の対話経路が消えるため、
      後回しにすると証跡ごと失う
   2. `terraform -chdir=terraform/ephemeral destroy`
   3. **実体確認**: `az containerapp replica list` 相当での実レプリカ消滅と
      `az resource list` での残存リソースゼロを確認（設定値でなく実体を見る = G4 の教訓）

   PostgreSQL（persistent）と退避済みデータ（＝証跡）は最後の最後まで残す。
   **旧版の「ops min 0 化 → 常駐停止」は削除**: min 0 でも ops のレプリカは落ちず active 課金が
   続くことが実測で確定済み（observations.md「G4 の訂正」/ ADR-0015 追記 #100）で、止血にならない
   （この自己矛盾は外部レビューが検出した。経緯は observations.md 同節の付記）

**判定則は (a) と (b) で分ける**（結論: 分けるべき。理由 — (a) はワースト日額 2.1 USD で、
検知が 2 日遅れても被害は約 4 USD に収まり、誤中断で観測の連続性を失う損失のほうが大きい。
(b) は 12 USD/日で、事後検知では開始した瞬間に余白 6 USD の超過が確定してから気づくことになり、
構造的に間に合わない）:

- **(a) 常時観測 = 事後検知型（従来どおり）**: 日次チェックで「estimated の日次差分 × 残日数 +
  既消費」が上限 75 USD を超える見込みが **2 日連続**になったとき発動（1 日分のラグ起因の振れで
  誤中断しない）
- **(b) イベント計測 = 事前予約型 + 壁時計強制終了**: 事後検知は適用しない。
  開始条件と強制終了は §6 の 1 / 1-b が正本（開始前に費用を全額予約し、開始後は課金表示と
  無関係に時刻で戻す）

**失効日が近づいたときの手順**（9/15〜: 証跡を取り切ってから畳む）:

1. 9/15: 観測データの最終エクスポート（観測テーブルのダンプ → `docs/verification/` 証跡化、
   probe ログ集計、Azure Monitor メトリクスの必要範囲エクスポート）
2. 9/16: ephemeral destroy → persistent destroy（旧計画 §5-6 の手順） → 残存リソースゼロ確認
3. 9/17: 課金反映ラグの分を待って最終コスト実測を記録（これも FinOps 証跡）

- マージン 2 日の根拠: teardown 失敗時の調査・再実行の余地 + 反映ラグ待ちで「最終消費額」を
  確定させるため。失効後はサブスクリプション無効化で**記録の取得自体ができなくなる**

## 10. 決定事項（2026-08-22 ユーザー決定）と本計画で結論を出した論点

### 10-2. 決定: /chat 保護 = (a) アプリ層 API キー + (d) 緊急遮断フラグの併設（#107）

### 10-3. 本計画で結論を出した論点（再掲）

- (b) は**時間を区切る**（2 日。§6 に根拠）— HA 多日常駐案は棄却（時間が計測値を良くしない）

  我々の書き込みレートで autovacuum の発火を複数回・バックアップの日次周期・probe の日内変動を
  各複数回含むこと。営業日変動のない合成負荷のため週次の季節性は考慮不要
- 採取先は DB 内観測テーブル・間隔は 5 分（pgstattuple のみ 1 時間）（§5-3 に根拠と観測者効果）
- teardown は 9/16（§9。マージン 2 日の根拠付き。観測を 9/15 まで延長しても動かさない = §2）
- 外部レビュー反映（2026-08-23）: 観測期間は日付固定でなく**相対時刻**（T_obs_start + 168h。§2）、

  時間・費用の削減優先順位は **(b) 再試行 → PITR 2 回目 → (b) 本体縮小**で一本化（§2）、
  最終手段は「証跡退避 → ephemeral destroy → 実体確認」（§9。min 0 は止血にならない実測に整合）
