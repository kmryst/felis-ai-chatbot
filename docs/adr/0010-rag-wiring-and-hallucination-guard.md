# ADR-0010: RAG 結線とコードで担保するハルシネーション・ガード

## ステータス

Accepted

## 日付

2026-08-19

## 決定内容

- `/chat` に RAG を結線する。ユーザー質問を embedding し、`documents` を pgvector の cosine 類似度（`<=>`）で検索して上位 k 件をコンテキストとして LLM に渡す
- **ハルシネーション・ガードをコードで担保する**: 検索結果が 0 件、または最上位の類似度が閾値未満の場合、**LLM を呼ばずに**固定文言（`NO_CONTEXT_NOTICE`）を返す
- k の既定値は **5**（`RAG_TOP_K` で上書き可能）
- 類似度閾値の既定値は **0.25**（`RAG_SIMILARITY_THRESHOLD` で上書き可能）。根拠は下記の実測スコア分布
- `object_properties` 全 53 行を決定的にレンダリングし、検索ヒット時のコンテキストへ常に併載する（entity 抽出は行わない）
- システムプロンプトに「回答本文に出典・参考文献の表記を書かない」を明示する（`NO_CITATION_INSTRUCTION`。ADR-0008 準拠）
- `documents.embedding` の backfill は `embedding IS NULL` の行のみを対象とする（冪等。`python -m app.ingest --embed`）。ingest の diff-sync で content が変わった行は削除・再挿入されて NULL に戻るため、ingest → backfill の順で実行すれば文面改訂も自然に再生成対象になる

## 背景: プロンプト指示だけではガードにならないことの実証

RAG 未結線（コンテキスト常時空）の状態で実 LLM（gpt-4.1-mini）に「観測史上いちばん高かった気温は？」と質問したところ、次の応答が返った。

> 観測史上いちばん高かった気温は、京都府福知山市で1933年（昭和8年）7月25日に記録された41.0℃です。これは日本での公式な最高気温の記録です。
> （参考：「気象庁｜過去の最高気温記録」）

取り込み済みの正しい記録は **41.8℃ / 群馬県伊勢崎 / 2025年8月5日**（`object_properties`）であり、値・地点・年月日すべてが誤り。さらに気象庁を出典として本文に自記しており、ADR-0008（回答ごとの出典表示は行わない）にも違反する。

システムプロンプトには「参照資料にない数値や事実を推測で補わない」と既に書かれていたが、**参照資料が 0 件のとき、モデルはそれを認識せず事前知識で埋める**ことが実証された。したがって「資料がないときに答えない」ことはプロンプトではなくコードで担保する。

## 類似度閾値 0.25 の根拠（実測）

embedding 生成後（38 行、text-embedding-3-small 1536 次元）、ドメイン内 4 問・ドメイン外 2 問の top1〜top5 類似度を実測した。

| 区分 | 質問 | top1 | top5 |
| --- | --- | --- | --- |
| 内 | 観測史上いちばん高かった気温は？ | 0.3572 | 0.3215 |
| 内 | 猛烈な雨ってどれくらい？ | 0.6340 | 0.5153 |
| 内 | 震度6強ってどんな揺れ？ | 0.6422 | 0.5753 |
| 内 | 台風の定義は？ | 0.5711 | 0.4994 |
| 外 | Python のリスト内包表記の書き方を教えて | 0.1487 | 0.1101 |
| 外 | おすすめのラーメン屋は？ | 0.1269 | 0.1198 |

ドメイン内の top1 最小値は 0.357、ドメイン外の top1 最大値は 0.149 で、分布は明確に分離している。閾値はほぼ中間の **0.25** とし、両側に約 0.1 のマージンを確保した。k=5 はドメイン内質問の top5 がいずれも閾値を大きく上回ること、およびチャンクが短い（中央値 143 文字）ため 5 件でも約 700 文字に収まることから採った。

## object_properties を参照する判断の根拠（実測）

`documents` 側チャンクだけで歴代最高気温の事実に到達できるかを、シード（`jma_seed.py` の `DOCUMENTS`）に対する文字列カウントで実測した。

| 検索語 | DOCUMENTS 内の出現数 |
| --- | --- |
| `41.8` | 0 件 |
| `伊勢崎` | 0 件 |
| `最高気温` | 0 件 |
| `気温` | 0 件 |

歴代最高気温は `object_properties`（object=気温 / property_name=record_highest_temperature）にのみ存在し、ベクトル検索では原理的に到達できない。したがって `object_properties` を参照する仕組みが必須である。

実装は最小限とし、**全 53 行（約 6KB）を決定的にレンダリングして常時コンテキストへ併載する**。質問文からの entity 抽出（対象オブジェクトの絞り込み）は行わない。理由:

- 53 行・約 6KB は gpt-4.1-mini のコンテキストに対して十分小さく、絞り込みの実益がない
- 部分文字列マッチ等の素朴な抽出は brittle で（例: 「猛烈な雨」に「大雨」は含まれない）、取りこぼしがハルシネーションの再発経路になる
- 5 日制約下で実装量を増やさない

`object_properties` は `source_id NOT NULL`（ADR-0003）により出典を JOIN 可能な状態を保つが、コンテキストには URL 等を含めない。回答ごとの出典表示は行わない方針（ADR-0008）のため、出典は検証・説明のために DB 側で引ければ十分である。

## HNSW インデックスの現状（実測。正直に記録する）

`EXPLAIN ANALYZE` の実測では、38 行の現規模ではプランナが Seq Scan（cost 6.08）を選択する。`SET enable_seqscan = off` で強制すると `documents_embedding_hnsw_idx` の Index Scan（cost 177.24）が使われることを確認しており、**インデックス自体は機能している**。小テーブルで Seq Scan が選ばれるのはコストベースで正しい動作であり、行数が増えれば自然にインデックスへ切り替わる。プランナ設定を歪めてまでインデックスを強制することはしない。

## 検討した選択肢

1. **類似度ガードをコードで実装 + object_properties 全件併載**（採択）
2. プロンプト指示のみで抑止 — 実測で機能しないことが実証済みのため不採択
3. entity 抽出による object_properties の絞り込み — brittle で実装量が増えるため不採択（上記）
4. object_properties にも embedding を持たせてベクトル検索へ統合 — マイグレーションと backfill 経路が増える。全件で 6KB の現規模では過剰設計のため不採択。データが増えたら再検討

## 影響

- 検索結果が閾値を満たさない質問には LLM を呼ばないため、ドメイン外質問のレイテンシとトークンコストがゼロになる
- ガードは `tests/test_app.py` で「LLM が呼ばれたら fail する」形で検証する（CI は常にスタブ。ADR-0004）
- 閾値・k は環境変数で調整可能。データ追加でスコア分布が変わった場合は再測定して既定値を見直す
